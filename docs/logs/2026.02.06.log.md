# 2026.02.06 - Config Shadowing, Logging Architecture, chart_logger Crash Fixes

## Summary

Debugged and fixed a chain of failures preventing multi-dataset analysis from completing. Root causes: config file shadowing, API misuse between `console_log` and `chart_logger`, case-sensitive struct field lookups, and unguarded persistent variables.

---

## Problem 1: `config.dataset_smoothing` Not Loading

### Symptom
Log output: `config.dataset_smoothing DOES NOT EXIST`. Per-dataset smoothing settings were ignored; all datasets fell back to defaults.

### Root Cause
Two `config.m` files existed:
- `C:\Coding\BGWRP\config.m` (root) -- the intended config, contains `dataset_smoothing` definitions
- `C:\Coding\BGWRP\src\config.m` -- stale copy, missing `dataset_smoothing` entirely

`BGWRP_Toolkit.m` line 17 runs `addpath(genpath(script_dir))` where `script_dir` = `src/`. This puts `src/` on the MATLAB path. When `config()` is called, MATLAB resolves to `src/config.m` (shadowing the root), so `dataset_smoothing` was never loaded.

### Fix
1. Merged unique values from `src/config.m` into root `config.m` (analysis windows for `PT01a_Recovery_short`, `PT01b_Recovery_short`; manual plot bounds; `config.use_si_units`).
2. Deleted `src/config.m`.

### Design Rule
There must be exactly ONE `config.m`, at the project root. `addpath(genpath('src'))` will shadow any file in `src/` that shares a name with a root-level file. Never place a `config.m` (or any filename that collides with the root) inside `src/`.

## Problem 2: `chart_logger` Calling `console_log` with Wrong Signature

### Symptom
`Invalid format. Location: console_log (line 60)` during plot generation.

### Root Cause
`chart_logger.m` was calling:
```matlab
console_log(log_file_handle, '=== CHART LOGGING SESSION ===\n');
```

`console_log` signature is `console_log(format_string, varargin)`. It interpreted `log_file_handle` (an integer like 3) as the format string, then called `fprintf(log_fid, 3)` internally, which MATLAB rejected as an invalid format.

### Fix
Changed `chart_logger.m` init/close sections to write directly to its own file handle:
```matlab
% Before (broken):
console_log(log_file_handle, '=== CHART LOGGING SESSION ===\n');

% After (fixed):
fprintf(log_file_handle, '=== CHART LOGGING SESSION ===\n');
```

### Design Rule
`console_log` is NOT `fprintf`. It does not accept a file handle as its first argument. Its API is:
- `console_log('init', filepath)` -- open log file
- `console_log(format_string, args...)` -- log to console + file
- `console_log('close')` -- close log file

Any code that needs to write to its own separate file handle must use `fprintf(fid, ...)` directly.

## Problem 3: `dataset_smoothing` Lookup Case Mismatch

### Symptom
Log: `No config found for test_label="PT01a_Recovery_short"` despite `config.dataset_smoothing.PT01A_RECOVERY_SHORT` existing.

### Root Cause
`analyze_das_data.m` used `test_label` (mixed case, e.g. `PT01a_Recovery_short`) directly as a struct field name. MATLAB struct field access is case-sensitive. The config keys are stored in UPPERCASE.

### Fix
`analyze_das_data.m` line 254:
```matlab
test_label_upper = upper(strrep(test_label, ' ', '_'));
if isfield(config.dataset_smoothing, test_label_upper)
```

### Design Rule
`config.dataset_smoothing` keys are UPPERCASE (e.g. `PT01A_RECOVERY_SHORT`). Any lookup must convert the test label with `upper(strrep(test_label, ' ', '_'))` first. See `config.m` lines 345-367 for the canonical key definitions.

## Problem 4: `chart_logger` Crashes on Uninitialized Persistent Variables

### Symptom
Two separate crashes at different execution points:
1. `chart_logger (line 96)` -- during regular message logging
2. `chart_logger (line 65)` -- during `chart_logger('close')` call

Both: `Operands to the logical AND (&&) and OR (||) operators must be convertible to logical scalar values.`

### Root Cause
`init_chart_logging.m` was modified to disable the separate chart log file (line 14: `chart_logger('init', config)` commented out). This means `chart_logger`'s persistent variables (`session_active`, `log_file_handle`) are never initialized and remain `[]`. MATLAB evaluates `[] && ...` as a non-scalar logical operation, which errors.

Two locations had this unguarded check:
- Line 65 (`'close'` branch): `if session_active && log_file_handle ~= -1`
- Line 96 (regular logging): `if session_active && ~isempty(log_file_handle) && log_file_handle ~= -1`

### Fix
Both lines now check `~isempty(session_active)` first:
```matlab
% Line 65 (close branch):
if ~isempty(session_active) && session_active && ~isempty(log_file_handle) && log_file_handle ~= -1

% Line 96 (regular logging):
if ~isempty(session_active) && session_active && ~isempty(log_file_handle) && log_file_handle ~= -1
```

### Design Rule
Any MATLAB function using `persistent` variables that may not be initialized must guard with `~isempty(var)` before any logical operation. `persistent` variables default to `[]`, and `[] && true` is a runtime error in MATLAB (unlike most languages where null/empty is falsy).

## Problem 5: Only One Dataset Getting Plots

### Symptom
`PT01a_Recovery_100` plots generated; `PT01a_Recovery_short` plots never created.

### Root Cause
Direct consequence of Problem 4. The `chart_logger` crash at line 65 (during the `'close'` call after PT01a_Recovery_100's plots) propagated up through `generate_plots` and was caught by the `try/catch` in `BGWRP_Toolkit.m` (line 2104), which terminated the entire analysis step. PT01a_Recovery_short was next in the iteration but never reached.

### Fix
Same as Problem 4. With the persistent variable guard in place, `chart_logger('close')` gracefully no-ops when uninitialized.

## Logging Architecture Reference

### Two logging systems exist:

| System | File | Purpose | State |
|--------|------|---------|-------|
| `console_log` | `src/_utils/console_log.m` | Primary log -- console + single file | Active |
| `chart_logger` | `src/_utils/chart_logger.m` | Chart-specific log -- separate file | Disabled (output routed to `console_log`) |

### `console_log` usage:
```matlab
% In run script (before BGWRP_Toolkit):
log_path = fullfile('C:', 'Coding', 'BGWRP', 'data', '_BATCH', '_log', 'console_log.txt');
console_log('init', log_path);   % Opens file, overwrites previous
console_log('message %s\n', x);  % Logs to console AND file
console_log('close');            % Flushes and closes
```

The log file is overwritten each run (not timestamped). Output path: `data\_BATCH\_log\console_log.txt`.

### `chart_logger` usage:
Currently disabled in `init_chart_logging.m` (line 14 commented out). All chart messages route through `console_log` instead. To re-enable the separate chart log file, uncomment `chart_logger('init', config)` in `init_chart_logging.m`.

### Why the MATLAB console is not usable:
The Cursor IDE MATLAB extension does not reliably surface `fprintf` output. `console_log` exists specifically to write a readable text file that Cursor can access. Any LLM working on this codebase should read `data\_BATCH\_log\console_log.txt` for pipeline output, not attempt to read the MATLAB console.

## Config Architecture Reference

### Single config file: `C:\Coding\BGWRP\config.m`

Called as a function: `config = config()`. Returns a struct.

Key sections:
- **Batch directories**: `config.test_labels`, `config.test_directories` (lines ~1-50)
- **Analysis time windows**: `config.analysis_windows.<DATASET_NAME>.start/.end` (lines ~270-310)
- **Manual plot bounds**: `config.manual_bounds.<DATASET_NAME>` (lines ~312-340)
- **Dataset smoothing**: `config.dataset_smoothing.<UPPERCASE_KEY>.fs/.preprocessing_window_sec/...` (lines ~345-367)

### Critical conventions:
1. `dataset_smoothing` keys are UPPERCASE: `PT01A_RECOVERY_SHORT`, not `PT01a_Recovery_short`
2. Directory names in `_active/` are mixed case: `PT01a_Recovery_short`
3. Any code looking up config by dataset name must normalize case with `upper(strrep(name, ' ', '_'))`
4. Never create a second `config.m` anywhere under `src/` -- it will shadow the root config via `addpath(genpath('src'))`
